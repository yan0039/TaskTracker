## 三、高频面试问答

> 每题的结构：**结论 → 实现 → 取舍/改进**。回答时尽量指向具体文件，例如「在 `TaskRepository` 里」「在 `TaskViewModel` 的 `stateIn` 里」。

### A. 项目与架构

#### Q1. 为什么选 Compose + Hilt + Room + DataStore 这套技术栈？

**答**：这是一个纯本地、单用户的 App，需求可以拆成四件事：声明式 UI、结构化数据持久化、键值偏好持久化、依赖装配。
- Compose 负责 UI 与状态驱动，避免 XML + findViewById 的样板代码；
- Room 适合任务这种有表结构、要查询和排序的数据，并且支持 `Flow` 可观察查询；
- DataStore 适合主题、开关这类少量键值，异步且事务化；
- Hilt 把 Room、DataStore、Repository、ViewModel 的创建统一到编译期依赖图，避免手写单例和工厂。

**取舍**：如果只是两三个页面，也可以不用 Hilt；但本项目的目的就是完整演示 Jetpack 五件套的协同，所以选了标准组合。

#### Q2. 为什么用单模块？如果拆多模块怎么拆？

**答**：当前代码量约 17 个 Kotlin 源文件、一个功能域，单模块能降低构建与配置成本，先保证分层清晰。
如果拆多模块，会按「稳定度」拆：
- `:core:model`、`:core:database`、`:core:datastore`、`:core:designsystem`（基础能力，被依赖）；
- `:feature:tasklist`、`:feature:addtask`（功能模块，只依赖 core）；
- `:app` 负责组装、导航与 DI 入口。

依赖方向是 `feature → core`，`:app → feature`；好处是编译隔离、可并行构建、边界不容易被破坏。Hilt 多模块用 `@InstallIn(SingletonComponent::class)` 的 Module 放在 core 里即可。

#### Q3. 分层怎么分的？依赖方向是什么？

**答**：按职责分包，不按类型分包：
- `data/local`：Room 的 Entity / Dao / Database；
- `data/preference`：DataStore 封装与主题枚举；
- `data/repository`：唯一数据入口，组合 Room 与 DataStore；
- `di`：Hilt Module，只负责「怎么创建实例」；
- `ui`：Compose 页面、ViewModel、主题、导航。

依赖方向严格单向：`ui → repository → local / preference`，`di` 只被用来装配，不允许 repository 反向依赖 ui。这样换数据源只改 repository，UI 无感知。

#### Q4. 为什么需要 Repository？ViewModel 直接调 Dao 不行吗？

**答**：行，但不该。三个理由：
1. **屏蔽数据源**：任务来自 Room、主题来自 DataStore，Repository 把它们对 UI 统一成一套接口；
2. **单一职责**：ViewModel 只管把数据转成 UI 状态，不该关心数据从哪来、怎么查；
3. **可演进 / 可测试**：将来加缓存或网络同步，只改 Repository；写测试时可以传入 Fake Repository，不需要真的 Room。

#### Q5. MVVM 和 MVI 的区别？为什么不用 MVI？

**答**：MVVM 里 ViewModel 暴露状态（本项目是 `StateFlow<TaskUiState>`），UI 通过回调上报事件；MVI 强调单向的 Intent → Reducer → State，所有交互都变成事件流。
本项目的交互只有增删改、切主题、切过滤，状态是有限且扁平的，用 MVVM + 单一 `StateFlow` 已经能保证「状态唯一、UI 只是投影」。如果页面有复杂表单、多来源异步事件、需要严格回放，MVI 的 reducer 会更可控，但也会带来更多样板代码。

#### Q6. 从点击「+」到列表出现新任务，完整链路是什么？

**答**：
1. `TaskListScreen` 的 FAB 触发 `navController.navigate("add_task")`；
2. `AddTaskSheet` 输入标题，点击「添加」调用 `TaskViewModel.addTask()`；
3. ViewModel 在 `viewModelScope` 里调用 `TaskRepository.addTask()`；
4. Repository 调 `TaskDao.insert()`（`suspend`，Room 调度到自己的线程池）；
5. Room 写入 SQLite，`InvalidationTracker` 感知 `task` 表变化；
6. 之前的 `observeAll(): Flow<List<Task>>` 重新发射；
7. ViewModel 的 `combine(tasks, themeMode, showDoneTasks)` 产生新的 `TaskUiState`，`stateIn` 缓存并推给 UI；
8. `TaskListScreen` 的 `collectAsStateWithLifecycle()` 收到新状态，Compose 重组，`LazyColumn` 渲染新行。

全程没有「手动刷新列表」的代码，这就是响应式单向数据流。

#### Q7. 如果加网络同步，架构怎么改？

**答**：保持「本地数据库是 UI 的唯一数据源」这一条不变：
- Repository 增加 `RemoteDataSource`，负责拉取/推送；
- 网络成功后写入 Room，UI 仍然只观察 Room 的 Flow；
- 同步策略可以放 `WorkManager`（重试、约束）、增量同步用 `updatedAt` 或服务端版本号；
- 需要错误状态时，把 Repository 的返回类型改成 `Result` 或在 ViewModel 增加 `error` 字段，而不是让 UI 直接处理异常。

这样 UI 与 ViewModel 基本不用改，符合「Repository 是唯一数据入口」的设计。

### B. Hilt

#### Q8. Hilt 在这个项目里具体做了什么？

**答**：它把「谁创建对象、谁持有引用」从手写变成注解：
- `TaskTrackerApp` 加 `@HiltAndroidApp`，生成依赖图根节点；
- `MainActivity` 加 `@AndroidEntryPoint`，允许向 Activity 及其 Compose 内容注入；
- `TaskViewModel` 用 `@HiltViewModel` + `@Inject constructor`，Hilt 自动把 Repository 传入；
- `TaskRepository` 用 `@Inject constructor`，Hilt 再递归找 `TaskDao` 和 `UserPreferences`；
- `AppModule` 用 `@Provides` 告诉 Hilt 怎么创建 Room 数据库和 DataStore 封装。

结果是全链路没有一个手写工厂或单例，且依赖缺失会在**编译期**报错，而不是运行时空指针。

#### Q9. 构造注入和 `@Provides` / `@Binds` 怎么选？

**答**：
- **构造注入**（`@Inject constructor`）用于自己写的类，如 Repository；Hilt 直接反射构造，不需要额外声明。
- **`@Provides`** 用于第三方类或需要手工装配的类，比如 `Room.databaseBuilder(...)`、需要 `Context` 的 `UserPreferences`。
- **`@Binds`** 用于「接口 → 实现」的绑定，比如定义 `TaskRepository` 接口、实现 `DefaultTaskRepository`，用 `@Binds` 更省代码。本项目 Repository 是具体类，所以没用到 `@Binds`。

#### Q10. `@Singleton` 和 `@ApplicationContext` 分别解决什么问题？

**答**：`@Singleton` 保证在 `SingletonComponent` 生命周期内只创建一个实例，Room 数据库和 DataStore 封装都必须是单例——DataStore 同文件多实例会直接抛 `IllegalStateException`，Room 多实例则会有连接和一致性问题。
`@ApplicationContext` 注入的是 Application 级 Context，长生命周期对象持有它不会泄漏 Activity；如果用 `@ActivityContext`，Repository/数据库就可能间接持有页面，造成内存泄漏。

#### Q11. Hilt 的组件层级是怎样的？

**答**：从外到内大致是 `SingletonComponent`（Application）→ `ActivityComponent` / `FragmentComponent` / `ViewComponent` / `ServiceComponent`，以及 `ViewModelComponent`（由 `@HiltViewModel` 使用）。
本项目的 Room、DataStore、Repository 装在 `SingletonComponent`；ViewModel 在 `ViewModelComponent`，随 ViewModel 销毁而释放。Scope 不能反向：Singleton 不能依赖 Activity 级对象。

#### Q12. KSP 和 kapt 有什么区别？为什么用 KSP？

**答**：kapt 基于 Java 注解处理器，要先为 Kotlin 代码生成 Java 桩（stub）再交给 javac，编译链路长、速度慢；KSP 直接理解 Kotlin 符号，不需要生成桩，通常更快，也更适合增量编译。
Room 2.6+ 和 Hilt 2.48+ 都完整支持 KSP，所以本项目 `ksp(libs.room.compiler)`、`ksp(libs.hilt.compiler)`。代价是 **KSP 版本必须和 Kotlin 版本严格对应**，本项目是 Kotlin 2.0.21 ↔ KSP 2.0.21-1.0.28。

#### Q13. 你实际遇到过 Hilt 的什么报错？

**答**：最典型的是「`TaskRepository cannot be provided without an @Inject constructor`」。原因是 Repository 的构造函数忘了加 `@Inject`，Hilt 找不到创建方式。排查顺序是：
1. 看构造函数有没有 `@Inject constructor`；
2. 看依赖类型有没有 `@Provides` 或构造注入；
3. 看 Scope 是否循环依赖（Singleton 依赖 Activity 级对象）；
4. 确认 `ksp(libs.hilt.compiler)` 和 Hilt 插件都配了。

这个坑我也写进了项目文档：参考的实战指南正文说「构造注入」，但示例代码漏了注解，直接编译不过。

### C. Room

#### Q14. Entity / Dao / Database 各自职责？为什么 Database 是抽象类？

**答**：
- `Task` 是 `@Entity`，描述表结构和字段；
- `TaskDao` 是 `@Dao` 接口，声明 SQL（Room 编译期生成 `TaskDao_Impl`）；
- `AppDatabase` 是 `@Database`，声明实体、版本，并暴露 Dao。

必须是抽象类，因为 `@Database` 标注的类要继承 `RoomDatabase`，而 `RoomDatabase` 本身是抽象类。实例由 `AppModule` 用 `Room.databaseBuilder` 创建，不让业务代码自己 new。

#### Q15. Room 的 Flow 是怎么感知数据库变化的？

**答**：Room 为返回 `Flow` 的 `@Query` 生成实现，内部通过 `InvalidationTracker` 注册观察者：它监听 `task` 表的失效事件，表数据一变就重新执行查询并发射新列表。
所以「查询返回 Flow」= 可观察查询；「返回普通类型」= 一次性读取。列表页必须用 Flow，否则增删后 UI 不会自动刷新。

#### Q16. `suspend` 和 `Flow` 有什么区别？需要自己 `withContext(Dispatchers.IO)` 吗？

**答**：`suspend` 用于一次性操作（insert/update/delete），Room 会调度到自己的查询/事务执行器，主线程不阻塞；`Flow` 用于持续观察查询结果。
**不需要**自己写 `withContext(Dispatchers.IO)`，Room 已经做了线程调度；手动再切反而多一层开销。真正需要自己切的是那些 Room 不管的操作，比如文件 IO 或网络。

#### Q17. `@PrimaryKey(autoGenerate = true)` 有什么坑？

**答**：自增主键时 `id` 的默认值要写 `0L`，表示「尚未插入」，Room 插入时会忽略这个值并回填真实 id；`insert` 返回新行的 rowId。
如果手动传了非 0 的 id，可能和已有行冲突；本项目 `insert` 用了 `OnConflictStrategy.REPLACE`，冲突时会覆盖原行，适合 Demo，但在真实业务里要谨慎，避免误覆盖。

#### Q18. 数据库升级怎么做？`fallbackToDestructiveMigration()` 有什么风险？

**答**：改表结构时把 `@Database(version = ...)` 加 1，并写 `Migration(old, new)`，在 `databaseBuilder` 上 `.addMigrations(...)`。
本项目为了 Demo 方便用了 `fallbackToDestructiveMigration()`——找不到迁移时会**清空数据库重建**，用户任务会丢，所以生产环境必须写 Migration。迁移要用 `MigrationTestHelper` 或 Room 的 schema 做测试，避免上线后崩溃。

#### Q19. 任务数据量很大时怎么优化？

**答**：当前是全量 `Flow` + `LazyColumn`，几千条以内没问题；再大要做三件事：
1. **索引**：给 `isDone`、`createdAt` 加索引，避免全表扫描和排序开销；
2. **分页**：用 Paging 3 的 `PagingSource` 直接从 Room 分页查询，UI 用 `LazyPagingItems`；
3. **减少无效重组**：`LazyColumn` 用稳定 key，状态粒度拆细，避免整页因一个字段变化而重组。

另外可以考虑只查需要展示的列（投影），减少对象分配。

#### Q20. 怎么测试 Room 的 Dao？

**答**：用 `Room.inMemoryDatabaseBuilder(context, AppDatabase::class.java).build()` 建内存库，`runTest` 里插入再查询，验证排序、过滤、更新。因为依赖 Android Context，这类测试一般放 `androidTest`（或 Robolectric）。
本项目的 DAO 测试还没补，目前只有 `ThemeMode` 的纯 JVM 单元测试；这是我下一步会补的部分。

### D. DataStore

#### Q21. DataStore 和 SharedPreferences 有什么区别？

**答**：
- **线程模型**：SharedPreferences 是同步 API，容易在主线程做磁盘 IO；DataStore 天生异步（读 Flow、写 suspend）。
- **一致性**：SharedPreferences 的 `apply()` 异步落盘，进程被杀可能丢；DataStore 是事务化写入，写完才发射。
- **异常处理**：DataStore 可以在 Flow 上 `catch`，SharedPreferences 解析失败可能直接崩。
- **订阅**：DataStore 直接 collect Flow，SharedPreferences 要手动注册监听器。

新项目应该优先用 DataStore。

#### Q22. Preferences DataStore 和 Proto DataStore 怎么选？

**答**：Preferences 存简单键值（主题、开关、计数），零配置、不需要 `.proto` 和额外插件，本项目用它；Proto 存结构化强类型对象，需要定义 `.proto`、配 protobuf 插件、实现 `Serializer`，适合结构会演进、需要跨版本兼容的场景。
一句话：**键值用 Preferences，结构化对象用 Proto**，不要混用同一个文件。

#### Q23. 为什么 DataStore 必须单实例？项目怎么保证？

**答**：同一个文件名的 DataStore 在进程里只能创建一个，否则会抛 `IllegalStateException: There are multiple DataStores active for the same file`。
本项目用顶层扩展属性保证：
```kotlin
private val Context.dataStore by preferencesDataStore(name = "user_preferences")
```
顶层委托只会初始化一次，再配合 `@Provides @Singleton` 注入 `UserPreferences`，从语法和 DI 两层保证单实例。

#### Q24. DataStore 读取抛异常怎么办？你的项目处理了吗？

**答**：推荐在 Flow 上 `catch`：
```kotlin
val themeMode = context.dataStore.data
    .catch { e -> if (e is IOException) emit(emptyPreferences()) else throw e }
    .map { ... }
```
当前项目没有加 catch，是一个可以改进的点；如果磁盘损坏或文件被占用，读取会向上抛异常。诚实回答「当时以功能验证为主，这里应该补异常兜底」。

#### Q25. Room 和 DataStore 都是持久化，为什么不用一个？

**答**：职责不同：Room 适合有表结构、需要查询/排序/事务/关系的数据；DataStore 适合少量配置项。
用 DataStore 存任务列表会失去查询、索引和事务能力；用 Room 存一个主题字段又太重。所以任务进 Room，主题和开关进 DataStore，由 Repository 统一对外。

#### Q26. 为什么不能用 `runBlocking` 读 DataStore？

**答**：DataStore 首次读取要读磁盘，`runBlocking` 会阻塞调用线程；如果在主线程就是 ANR 风险。UI 侧应该用 `Flow` + `collectAsStateWithLifecycle()` 订阅，写入用 `suspend` 函数在 `viewModelScope` 里执行。

### E. ViewModel / Flow / 协程

#### Q27. StateFlow、LiveData、SharedFlow 怎么选？

**答**：
- **StateFlow**：热流、始终有当前值、相同值会合并，适合 UI 状态；本项目 `uiState` 就是 `StateFlow<TaskUiState>`。
- **LiveData**：生命周期感知，但属于 Android 体系、线程约束多，和 Compose/协程配合不如 StateFlow 自然。
- **SharedFlow**：支持 replay、多个订阅者广播，适合一次性事件（导航、Toast）；注意事件不要用 StateFlow，否则旋屏会重放。

#### Q28. `combine` + `stateIn` 解决了什么问题？

**答**：`combine` 把任务列表、主题模式、是否显示已完成三个 Flow 合成一个 `TaskUiState`，UI 只订阅一个对象，避免多个 `collect` 和状态不一致。
`stateIn` 把它转成热 `StateFlow`，并缓存最新值；`initialValue = TaskUiState()` 让首帧有默认状态，不会出现空指针或「未初始化」的分支。`viewModelScope` 作为作用域，ViewModel 清除时自动取消。

#### Q29. `SharingStarted.WhileSubscribed(5_000)` 是什么意思？

**答**：当最后一个订阅者消失后，延迟 5 秒再停止上游数据流。这样旋转屏幕、短暂切后台再回来时，不会立刻重建 Flow、重新查数据库，避免闪烁和重复 IO；超过 5 秒才真正释放资源。这是官方推荐的折中值。

#### Q30. 为什么用 `collectAsStateWithLifecycle()` 而不是 `collectAsState()`？

**答**：前者会跟随生命周期，在页面进入后台（STOPPED）时自动停止收集，回到前台再恢复；后者会一直收集，后台也在重组、占用资源。Compose + AndroidX Lifecycle 的标准做法是前者。

#### Q31. `viewModelScope` 的原理？页面销毁后协程会怎样？

**答**：`viewModelScope` 是 ViewModel 的扩展属性，内部用 `SupervisorJob() + Dispatchers.Main.immediate`，并在 `onCleared()` 时取消。页面销毁（ViewModel 被清除）后，里面启动的协程会自动取消，不会泄漏。
注意：配置变更（旋屏）时 ViewModel 不会清除，协程继续运行，这也是数据不丢的原因。

#### Q32. Snackbar 这类「一次性事件」你怎么处理？

**答**：本项目把 `onShowMessage: (String) -> Unit` 从 `AppNavHost` 传给页面，页面在操作成功后调用，最终执行 `snackbarHostState.showSnackbar()`。这种回调方式简单直接，适合单页面触发。
更通用的方案是用 `Channel`/`SharedFlow` 发事件，在 UI 侧用 `LaunchedEffect` 收集；要点是事件不能重放（旋屏不应重复弹），也不能用 StateFlow 承载。

#### Q33. 为什么旋屏后数据还在？ViewModel 为什么不会被销毁？

**答**：Activity 因配置变更重建时，`ViewModelStore` 由 `NonConfigurationInstances` 保留下来，旧的 ViewModel 被复用，所以 `StateFlow` 里的数据和协程都还在。页面重新组合时 `collectAsStateWithLifecycle()` 重新订阅，立刻拿到当前值。

### F. Compose

#### Q34. Compose 的重组机制是什么？

**答**：首次组合会执行所有 `@Composable` 生成 UI 树；之后当读取的 `State` 变化时，Compose 只重新执行**读取了该状态的那部分** Composable（按重组范围），并跳过参数稳定的调用。所以性能优化的核心是：状态粒度合理、参数稳定、避免在组合中做重活。

#### Q35. Compose 里的状态应该放在哪？

**答**：分三层：
- **UI 瞬时状态**（输入框文字、弹窗开关）：`remember { mutableStateOf }`；
- **需要跨配置变更保存的 UI 状态**：`rememberSaveable`（走 Bundle）；
- **业务状态**（任务列表、主题、过滤）：ViewModel + `StateFlow`；
- **持久状态**：Room / DataStore。

原则是「Composable 只渲染和上报事件，不持有业务逻辑」。

#### Q36. `LazyColumn` 为什么一定要传 key？

**答**：key 是列表项的身份标识。用任务 `id` 做 key，删除、插入、排序时 Compose 能复用正确的 item 和内部状态（比如输入框、动画），不会出现「状态串行」或整个列表重建。`contentType` 还可以帮助不同类型的 item 复用。

#### Q37. `TaskUiState` 是 data class，就一定可以跳过重组吗？

**答**：不一定。Compose 判断的是**稳定性**：`data class` 只是值语义，不代表编译器认为它 stable；`TaskUiState` 里的 `List<Task>` 是接口类型，Compose 编译器通常视为 unstable，导致读取它的 Composable 不能被跳过。
改进方向：用 `kotlinx.collections.immutable` 的 `ImmutableList`，或给类加 `@Immutable` 并保证字段真的不可变，或把状态拆细、用 `derivedStateOf` 降低重组范围。

#### Q38. Modifier 的顺序为什么重要？举个例子。

**答**：Modifier 是从左到右包裹的，顺序不同效果不同。例如 `Modifier.padding(16.dp).background(Red)` 是先留白再画红底（红底不含 padding 区域），而 `Modifier.background(Red).padding(16.dp)` 是红底铺满再内缩内容。`clickable` 放在 `padding` 前后也会改变点击热区大小。

#### Q39. `@OptIn(ExperimentalMaterial3Api::class)` 是什么？为什么用 ModalBottomSheet？

**答**：`@OptIn` 表示「我知道这个 API 还标记为实验性，但我确认使用」。`ModalBottomSheet` 和 `TopAppBar` 在 Material3 1.3.1 中仍标注 `@ExperimentalMaterial3Api`，不是废弃 API，而是官方保留调整空间。
选择 ModalBottomSheet 是因为新增任务是一个轻量、可中断的操作，底部弹窗比整页跳转更符合 Material 规范；本项目把它做成独立导航目的地，返回栈和系统返回键都能自然工作。

#### Q40. 主题是怎么实现的？深色模式下系统栏怎么处理？

**答**：`ThemeMode`（SYSTEM / LIGHT / DARK）存在 DataStore，`TaskTrackerTheme` 根据模式选择 `lightColorScheme` 或 `darkColorScheme`，`SYSTEM` 时用 `isSystemInDarkTheme()`。
系统栏在 `SideEffect` 里同步：设置导航栏颜色为当前背景色，并用 `WindowCompat.getInsetsController(...).isAppearanceLightStatusBars/NavigationBars` 切换图标明暗。这样深色主题下不会出现「页面是黑的、导航栏还是白的」。

#### Q41. 边到边（edge-to-edge）是怎么做的？

**答**：`MainActivity` 调用 `enableEdgeToEdge()`，让内容延伸到状态栏和导航栏后面，并处理系统栏图标明暗和刘海区域。内容侧用 `Scaffold` 的 `innerPadding`、`navigationBarsPadding()` 等 insets 处理避免被遮挡；本项目还处理了 Snackbar 与 FAB 的避让。

#### Q42. Compose 性能问题怎么排查？

**答**：先用 Layout Inspector 的 recomposition counts 看哪些 Composable 在频繁重组；再看参数是否稳定（List、lambda 捕获）；用 Compose compiler metrics 检查哪些类被标记 unstable；必要时用 `derivedStateOf` 减少派生状态触发重组的次数。真机首帧还可以配合 Baseline Profile / Macrobenchmark。

### G. Navigation 与页面细节

#### Q43. 两个目的地是怎么定义的？把 ModalBottomSheet 做成路由有什么利弊？

**答**：`Routes` 里定义 `task_list` 和 `add_task`，`NavHost` 用 `composable` 注册。列表页 FAB `navigate("add_task")`，添加页 `onDismiss`/`onAdded` 时 `popBackStack()`。
**好处**：返回栈天然正确，系统返回键、转场都由 Navigation 处理，Snackbar 也能跨页面。
**代价**：弹窗退出时是路由直接 pop，动画不如同屏 sheet 细腻；如果只是简单表单，也可以在同屏用 `rememberModalBottomSheetState` 控制显隐，不占路由。

#### Q44. Snackbar 为什么放在 NavHost 外层？

**答**：Snackbar 是跨页面的全局反馈。如果放在列表页内部，跳转或返回时页面销毁，提示会中断；放在 `AppNavHost` 的 Scaffold 里，任何页面的提示都能完整显示。本项目还把 Snackbar 上移，避免盖住 FAB。

#### Q45. 添加任务时连续点两次「添加」会怎样？怎么防？

**答**：当前实现点击后会 `addTask()` 并立即 `popBackStack()`，正常情况下第二次点击已经离开页面；但在极端快速双击下，仍可能插入两条。更稳妥的做法是：点击后立刻禁用按钮（`isSubmitting` 状态），或用 `debounce`/一次性事件消费，保证同一个提交只执行一次。

### H. 测试与工程化

#### Q46. 你写了哪些测试？还缺什么？

**答**：目前有 `ThemeModeTest`，验证持久化字符串到枚举的映射（包括 null、非法值、大小写敏感），这是纯 JVM 测试，跑得很快。
还缺：ViewModel 测试（`kotlinx-coroutines-test` + Turbine 验证 `uiState` 发射）、Room DAO 测试（in-memory 数据库）、Compose UI 测试（`createAndroidComposeRule` 点击 FAB、输入、断言列表）。这是我下一步会补齐的。

#### Q47. 为什么用 Gradle Version Catalog？

**答**：把版本号和坐标集中到 `libs.versions.toml`，模块里只写 `libs.xxx` 别名，避免多处版本不一致；IDE 有补全和跳转，升级时只改一处；也便于团队统一依赖。比 `ext` 变量更类型安全。

#### Q48. Lint 报过什么错？怎么修的？

**答**：`UnusedMaterial3ScaffoldPaddingParameter`：外层 Scaffold 的 `innerPadding` 没用。修法是把外层 Scaffold 的 `contentWindowInsets` 设为 0（系统栏内边距交给内层页面处理），同时把 `innerPadding` 传给 NavHost，并给 Snackbar 加 `navigationBarsPadding()`，既满足 Lint 又避免双重内边距。最终 `lintDebug` 0 error。

#### Q49. 这套版本是怎么保证兼容的？

**答**：三条线：
1. **AGP ↔ Gradle**：AGP 8.7.3 需要 Gradle 8.9+，项目用 Gradle 8.9；
2. **Kotlin ↔ KSP**：KSP 版本号必须等于 Kotlin 版本加后缀，`2.0.21` ↔ `2.0.21-1.0.28`；
3. **Kotlin 2.0+ 的 Compose 编译器**：由 `org.jetbrains.kotlin.plugin.compose` 提供，版本跟随 Kotlin，不再写 `composeOptions.kotlinCompilerExtensionVersion`。

另外 compileSdk 35 需要 AGP 8.6+，JDK 需要 17。

## 四、可以主动讲的三个「难点故事」

面试官问「讲一个你解决的问题」时，从下面挑一个，按 **现象 → 定位 → 解决 → 收获** 讲：

### 故事 1：深色主题下导航栏还是白的

- **现象**：切到深色主题后，页面变黑，但底部系统导航栏仍是白色，很割裂。
- **定位**：`enableEdgeToEdge()` 默认按**系统**明暗设置系统栏 scrim，App 内的 Compose 主题切换不会自动同步系统栏。
- **解决**：在 `TaskTrackerTheme` 的 `SideEffect` 里，根据 `darkTheme` 设置导航栏颜色和 `isAppearanceLightStatusBars/NavigationBars`。
- **收获**：Compose 主题和 Window 级系统 UI 是两套体系，需要显式桥接。

### 故事 2：Snackbar 盖住 FAB，Lint 还报错

- **现象**：新增/删除后的 Snackbar 正好压在右下角 FAB 上；同时 Lint 报 `UnusedMaterial3ScaffoldPaddingParameter`。
- **定位**：外层 Scaffold 只放 Snackbar，`innerPadding` 被忽略；Snackbar 默认贴底，没有给 FAB 留位。
- **解决**：外层 `contentWindowInsets = WindowInsets(0)`，把 `innerPadding` 传给 NavHost（此时为 0），Snackbar 加 `navigationBarsPadding()` + 88dp 底部留白；页面内边距仍由内层 Scaffold 处理。
- **收获**：嵌套 Scaffold 的 insets 要明确「谁负责」，否则不是双重内边距就是遮挡。

### 故事 3：指南代码跑不起来

- **现象**：按指南抄完，`assembleDebug` 直接失败：找不到 `collectAsStateWithLifecycle`、Hilt 说 Repository 无法提供、Manifest 解析失败。
- **定位**：依赖清单漏了 `lifecycle-runtime-compose`；Repository 构造函数漏 `@Inject`；Manifest 把注释写进了 `<application>` 属性列表；图标资源缺失。
- **解决**：逐条对照编译错误修复，并补了 `@OptIn`、`HorizontalDivider`，最后用 Lint 和模拟器验收。
- **收获**：教程代码不能无脑信，编译器和 Lint 是最好的老师；也让我记住了「Kotlin ↔ KSP ↔ AGP ↔ Gradle」的版本对应。
